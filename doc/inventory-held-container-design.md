# 背包、手持与容器

拾取、随身携带、拿在手上、存进箱子这四件事的设计与实现约定。

这套东西的参照物是《饥荒》：物品是数据、动作由组件声明、权威只在服务端。但有两处
刻意不照抄——它是 2D 换贴图，我们是 3D 挂 Actor；它用七八条槽位 RPC 支撑拖拽，
我们不做拖拽。

## 0. 四条不变量

1. **权威只在房间 DS。** 客户端发意图，不发结果。拿没拿到、扔了多远、箱子里还剩
   几个，都由服务端说了算，客户端靠快照跟随，不做本地预测。
2. **「按下去会发生什么」只有一个答案来源**，见 §2 的动作表。界面拿它出提示，
   服务端拿它选 handler。
3. **物品是配置，不是代码。** 新增一件道具 = 往 `config/items/item-catalog.json`
   加一条 + 一枚图标。背包、拾取、手持、使用、界面都不用改。
4. **键位不写死在玩法里。** 物品说自己走哪个*逻辑输入槽*，物理键位归
   `config/input/player.input.json`——重绑定、手柄、触屏三套映射只有在那里才生效。

## 1. 物品与账本

### 1.1 物品目录

`config/items/item-catalog.json`，两端读同一份，所以「木头堆到几个」「蘑菇一格装几朵」
永远是同一个答案，不需要为物品参数再走一次复制。

字段：

| 字段 | 含义 |
| --- | --- |
| `holdable` | 能不能拿在手上。默认真，弹药默认假（按发数记的池子没有「一发拿在手上」） |
| `durability` | 耐久度。0 或不写 = 用不坏。**现在四件物品全是 0**：没有「用一次掉一点」的系统，写别的数只会是一个空承诺 |
| `use` | 怎么用它。整块不写 = 只能拿着，按键没反应 |
| `ammo` | 弹药位：吃哪几种弹药、装几发。整块不写 = 它不吃弹药。见 §1.3 |

`use` 的形状就是 §4 的全部输入：

```json
"use": {
  "action": "eat",        // eat | shoot | tool | throw —— 只登记有人兑现得了的动词
  "input": "primary",     // 逻辑输入槽，不是物理键
  "mode": "hold",         // tap 点一下 / hold 圈满即结算 / charge 圈满等松手
  "holdSeconds": 1.2,     // hold 与 charge 必填：圈画满要多久
  "cooldownSeconds": 0.5, // 可选：用完多久才能再用一次。0 或不写 = 没有冷却
  "value": 1              // eat 是一次吃掉几个；tool 是额外采集伤害；throw 是初速度的十倍
}
```

### 1.1.1 目录里现在有什么

设计稿 `designer-inventory.md` 的物品表就是目录的全部内容，一条不多：

| 物品 | 分类 | 堆叠 | 用法 | 世界里长什么样 |
| --- | --- | --- | --- | --- |
| 木头 `wood` | 材料 | 10 | 不能使用 | 棕色六棱柱，躺着会滚（砍树掉的就是它） |
| 石头 `stone` | 材料 | 10 | 不能使用 | 压扁的低多边形石子（敲岩石掉的就是它） |
| 果子 `fruit` | 补给 | 10 | 按住 1.2 秒吃掉一个 | 带梗的苹果（果树掉的就是它） |
| 蘑菇 `mushroom` | 补给 | 3 | 按住 1 秒吃掉一个 | 菌盖加菌柄，和地里长着的那朵同一副样子 |
| 弹弓 `slingshot` | 工具（独立池） | 1 | 蓄力 0.9 秒，松手打出一发石头，冷却 0.5 秒 | Y 形树杈，两个杈头之间绷着皮筋 |

**一件物品一个掉落原型**：`findItemArchetypeId` 按 `itemStack.itemType` 反查原型，
同一种物品有两个原型时它只会挑到其中一个，手上那件和地上那堆就会长得不一样。

**手持与掉落是同一副模型**，因为它们本来就是同一个原型：`heldItemArchetype` 把
物理、生命期、可交互摘掉，只留渲染（见 §4.2）。所以「木头拿在手上是什么样」不是
一份新配置，是同一根六棱柱。

`throw` 与 `tool` 两个动词还在（投掷抛体、工具采集都是跑得通的系统），但**目录里
暂时没有物品在用它们**——物品表上没有投掷物，弹弓走的是 `shoot`。等它们回来时，
加的是目录里的一条数据，不是代码。

`shoot` 是唯一一条**物品系统自己不兑现**的动词：弹丸怎么飞、打中了怎么样归武器
系统，它自己注册执行器（§4.6）。物品系统这一侧负责的是执行器跑之前和跑之后的
全部——授予、判定激活时刻、算蓄力比例、扣货扣弹药。

### 1.2 `ItemLedger`：背包和容器共用的记账

背包和箱子装的是同一种东西、守的是同一套堆叠与货位规则，区别只有容量和归谁所有。
所以记账逻辑抽在 `shared/actor/ItemLedger.mjs`，`InventoryComponent` 和
`ContainerComponent` 各持有一份——改一次堆叠规则，两边同时生效。

`ItemLedger.remove` 按账上实际有的数量截断而不是报错。这一条是 §5 多人共享容器
不需要锁的全部原因。

### 1.3 弹药记在格子上，不记在物品目录里

同一把弹弓，装着三颗石头和空着是两种状态，而这两种状态属于**那一把**，不属于
「弹弓」这个种类。所以账本里的一条可以带一段 `ammo: { itemType, quantity }`，
物品目录里的 `ammo: { accepts, capacity }` 只说「这种东西吃什么、装几发」。

**只有 `slotCost: 0` + `stackLimit: 1` 的物品能写 `ammo`**（也就是分类里的工具）。
一格里堆着两把弓时，装进去的石头归哪一把答不上来；而独立池每种只有一条，
「背包里的那一把」因此永远只有一把——`{ kind: 'backpack', itemType }` 就寻址得到它，
不需要给每一件东西编一个实例 id。

`accepts` 写的是**物品 id**，不是分类：弹弓吃的是普通石头，而石头是材料。
「什么算弹药」由吃它的那件东西说了算。

| 做什么 | 谁 |
| --- | --- |
| 这一格现在装着什么 | `InventoryComponent.ammoAt(ref)` |
| 装填（从另一格搬过来） | `loadAmmo(target, source)`，一次尽量装满，装不下的留在来源 |
| 卸下（按拾取的落点回身上） | `unloadAmmo(target)`，一发都收不下就整件事不做 |
| 打掉几发 | `consumeAmmo(target, count)` |
| 整条搬走 / 放回（弹药跟着走） | `ItemLedger.takeEntry` / `putEntry` |

`ref` 的形状是 `{ kind: 'hotbar', slotIndex }` 或 `{ kind: 'backpack', itemType }`，
和界面上那一格（`InventorySlotRef`）、命令里的地址是同一个——所以「哪一格」这件事
在三层之间不需要翻译。

**装了弹药的那一条不和同类合并**：它已经不是「一把普通的弹弓」了，合并会让那几发
凭空变成两份或一份。装配到物品栏、收回背包、存进箱子，弹药都跟着那一格走。掉落物
身上还没有弹药位，所以**丢下时先把弹药卸回身上**（收不下的那些跟着掉在地上）——
等掉落物真的能记住「哪一件」再改成跟着走。

## 2. 动作表：`shared/actor/ActorActionTable.mjs`

对应《饥荒》的 `componentactions.lua`。

**它解决的问题**：在此之前，「看着这个东西时按 E 会发生什么」的状态判断写了两遍
——`ActorInteractionController.resolvePrompt` 出提示一遍，`ServerScene.interactWithActor`
分派一遍。两份判断没有任何机制保证一致，漂移的表现是界面写着「叼住」而服务端拒绝，
或者反过来提示不出但按下去有反应。

```js
resolveActorAction(target, context) -> { id, verb, blocked } | undefined
```

- `target` 是候选 Actor 的**复制态**（两端都拿得到的那部分）
- `context` 是发起方状态（是谁、接管着哪台载具）
- 客户端拿 `verb` 出提示，服务端拿 `id` 选 handler，两端共用同一个 `blocked` 判定

**它不做距离判定**：距离要拿权威位姿算，只能在服务端做。客户端算出来的是给玩家看
的预期，不是许可。

动作 id 与触发条件：

| `interactable.action` | 状态 | 动作 id | 动词 |
| --- | --- | --- | --- |
| **任意** | 是我手上那件 | `drop-held` | 放下「X」 |
| `mushroom-bite` | 我拉着 | `mushroom-release` | 松开「X」 |
| | 别人拉着 | — | 「X」正被叼住（blocked） |
| | 空闲 | `mushroom-grab` | 叼住「X」（拉住它才谈得上拔，见 §4.4.1） |
| `pickup-stack` | — | `pickup-stack` | 拾取「X ×3」 |
| `harvest-prop` | — | `harvest-prop` | 砍伐「X」 |
| `container-open` | — | `container-open` | 打开「X」 |
| `cargo-toggle` | 没接管载具 | — | 先接管木筏（blocked） |
| | 空闲 | `cargo-load` | 装载「X」 |
| | 我的载具装着 | `cargo-unload` | 卸载「X」 |
| | 别人的载具装着 | — | 已被其他木筏装载（blocked） |

第一行排在 `switch` 之前，而且不看 `enabled`：手上那件东西的 `interactable` 是关着的
（不参与就近搜索），但**一个已经建立的持续状态必须有一个确定的退出入口**——否则
拿起来的东西再也放不下。它压过所有其它分支，所以叼着的蘑菇和快捷栏拿出来的手持物
走的是同一条退出路径。

## 3. 拾取流程

一次拾取穿过的完整链路，每一步的归属：

```
组件声明动作      InteractableComponent.action        （原型 JSON）
    ↓
出提示            resolveActorAction → HUD            （客户端，只读）
    ↓
发意图            actor:interact {actorId, sequence}  （客户端）
    ↓
限流 + 路由       RoomConnectionHub → 房间子进程       （服务端）
    ↓
校验              序号、目标存在、动作表、距离          （ServerScene）
    ↓
变更              ItemLedger.add / prop.harvest       （权威 Component）
    ↓
确认              下一帧快照                           （只发给该发的人）
    ↓
重画              revision 变了才重画                  （客户端界面）
```

和《饥荒》的差别只有一处：它由 `locomotor` 自动走到 `action.distance` 之内再执行，
我们直接按当前距离判定、超距就拒绝。自动寻路会和这里的客户端预测移动打架。

**满额时不拾取**：`ItemLedger.add` 收下多少返回多少，收不下的部分留在世界里。
背包满了地上那堆不会消失，也不会静默吞掉。

### 3.1 捡起来的东西落在哪：先手上，再物品栏，最后背包

`InventoryComponent.receive` 是拾取唯一的入账口，落点顺序是：

1. **已经装着同种、还装得下的物品栏格**——手上正拿着同一种东西时，这一步就是
   「堆在手上那一摞上」；
2. **空着的选中格**（空手），并顺手切过去：空手捡起一块石头，石头就该出现在手上；
3. 其余物品栏空格；
4. **背包**。

第一去处是手上而不是背包，因为捡起来的东西十有八九是马上要用的：落进背包等于
要求玩家每捡一次就开一次背包、装配一次、再切一次格。每一步都按堆叠上限部分收下，
收不完的往下走；四步都收不下才返回 0，剩下的留在世界里。

**手上已经握着别的东西时不换手**：玩家没有要求换，一次路过的拾取不该把手上那件
顶掉。所以只有「本来就空着手」的那次才会顺带切格。

## 4. 手持与快捷栏

### 4.1 快捷栏格子里存的是 `itemType`

不是某一堆的下标。三个理由：

- 背包界面是自动分类排序的，没有稳定的「第几格」可以引用；
- 容器被两个人同时翻时，下标会错位，`itemType` 不会；
- 一种物品用光之后配置仍然留在格子上，补货回来就还在原位。

所以「手上到底有没有东西」是推导出来的：`hotbar[activeIndex]` 这件东西在账本里
还有没有。用光了手就空着，格子仍然记着配置。

### 4.2 手持物在世界里是一个真 Actor

照搬蘑菇那条路：`PickupDropComponent.heldActorId` + `world.setActorParent` 挂到
角色的嘴部/手部挂点，局部坐标来自持有者原型。切走、丢下、离开房间的处置也复用
蘑菇已经踩过的那几条（不建刚体、不登记碰撞盒、落点推到身体之外）。

因此**嘴上同时只有一件东西**：叼着蘑菇时不能再拿快捷栏物品，反之亦然。这不是限制，
是让 `drop-held` 有唯一含义的前提。

### 4.3 切换

| 输入 | 行为 |
| --- | --- |
| 数字键 1-9 | 切到第 N 格；再按一次同一格 = 收手 |
| 手柄 LB / RB | 前后循环 |
| 背包界面点一下某件物品 | 放上快捷栏并立刻握在手上 |

### 4.4 丢出键：一个键一件事

| 键 | 含义 | 手上有东西时 |
| --- | --- | --- |
| 交互键（E / ACT / Y） | 和世界互动：拾取、采集、开箱、叼住 / 松开 | **不变** |
| 丢出键（Q / DROP / LT） | 把手上那件放到身前地上 | 按一下就掉 |

**放下有自己的一个键。** 它曾经和交互键挤在一起，先是「短按放下、长按收进背包」，
后来是「手上有东西时按下即放下」。两版都有同一个毛病：「和世界互动」和「处理手上
那件」本来就是两条独立的判断，共用一个键就只能二选一——要么一次按下同时做两件事
（手上那件掉出去，脚下那堆又被捡回来），要么让其中一条把另一条整个盖掉（手上一有
东西，交互键就再也够不到脚下那堆货）。分成两个键，两条判断各自独立，一次按下永远
只有一个结果。

因此 `ActorInteractionController` 在解析候选时**跳过 `drop-held`**：手上那一株只有
在交互键真的能对它做点什么时（拉着的那株按一下是「松开」）才占住候选，其余情况直接
让开。`HotbarController` 那条丢出键则只看嘴上有没有东西——它认得两种手持物（物品栏
的表现体、叼着的世界物件），发的是同一条 `drop` 命令。

「收回背包」不在任何一个键上：打开背包，在那一格上点「收回背包」，或者把它拖回背包
那一片（§6.1）。它不是一个赶时间的动作，不值得占一个键，更不值得压在另一个动作下面。

### 4.4.1 世界物件怎么进背包

蘑菇不是物品堆，没有 `itemType`。「这个世界物件装进包里算哪种物品」写在**物件
自己身上**（`StowableComponent`），而不是背包或某张转换表里：一株蘑菇装进包里算
什么，是这株蘑菇的属性；背包只需要问它，不需要认识世界上所有能被揣走的东西。

没挂这个 Component 的物件就是揣不走的：拔断之后它只能叼在嘴上，再按一次放下。

### 4.4.2 拔出来的东西直接进物品栏

**空手**拉住一株蘑菇、拖到拉断，得到的是**物品栏里的一朵蘑菇**，而不是一个还要
再按一次才处理得掉的世界物件（`ElasticDetachSystem` → `ServerScene.stowPulledActor`）。

- 「只有空手拔得出来」不需要额外判断：拉住那一步本来就要求嘴里空着，而手上握着
  物品栏那一格时嘴上挂着表现体，那条路走不到拔断。
- 落进哪一格由 `InventoryComponent.equipToHotbar` 决定：**已经装着同种且装得下的
  那一格 → 空着的选中格 → 第一个空格**。玩家说的「空手对应的那一格」就是选中的
  那一格，所以拔完就握在手上，不用再按一次数字键。
- 它**不经过背包**：那朵蘑菇刚从世界里出来，账上本来就没有它。要求它先落进背包
  再搬一次，只会让「空手拔一朵、拔完就在手上」在背包满的时候莫名其妙地失败。
- 物品栏一格都腾不出来时**退回原来那条**：叼在嘴上，等玩家再按一次放下。凭空把
  它删掉等于让玩家白拔一次。

挂手持模型这一步排到本轮 System 跑完之后（`ServerScene.flushHeldItemSyncs`）：
拔断发生在 System 迭代中途，`ActorWorld` 那时把增删排队，当场挂会拿到一个还没进
世界的 Actor。

放下也因此要分派：物品堆摆好位置交给掉落物理，世界物件走它自己那套（建刚体、
恢复可交互、按碰撞半径把落点推到身体之外）。分派收在 `dropHeldObject` 一处，
让调用方自己判断拿的是哪一种，那个判断迟早会有一处忘了写。

收回背包时如果背包正好满了，**东西留在手上**而不是消失。

### 4.5 使用：一条临时授予的能力

使用一件物品不是「按键的一个分支」，而是一条完整的能力生命周期：

```
授予（arm）→ 按物品配置激活（tap 点一下 / hold 圈满 / charge 松手）→ 完成后收回
```

两个入口共用这条路径，区别只在货从哪扣：**物品栏**（切到某一格就授予那一格的
用法，扣那一格）和**背包**（菜单里点「使用」授予一次，扣背包那一摞，全程不经过手）。

`use.input` 是**逻辑输入槽**（目前只有 `primary`），由客户端映射到输入方案里的
Action 标签；物理键位、手柄按钮、触屏按钮三套映射都在
`config/input/player.input.json`，物品目录一个键都不写死。

一次使用对应的输入相位：

| 相位 | 客户端 | 服务端 |
| --- | --- | --- |
| `started` | 记下本地按下时刻，开始画那圈圆形倒计时 | 记下权威按下时刻 |
| 每帧 | 按 `holdRatio` 更新圈 | 倒计时走完那一刻**自己激活** |
| `completed` | 收掉圈；圈已经满过就什么都不发 | `tap` 与 `charge` 在这里激活；`hold` 没走完 = 取消 |
| `canceled` | 收掉圈 | 丢弃这次按下 |

**激活发生在倒计时走完那一刻，不是松手那一刻。** 两端跑同一个
`holdRatio(heldSeconds, holdSeconds)`，所以圈画满那一刻就是服务端激活那一刻，
但判定用的是服务端自己的计时——客户端上报的时长只用来对齐表现。

`tap` 是 `holdSeconds = 0` 的退化情形，`holdRatio` 恒返回 1——不需要单独一条支路。

**`charge` 和 `hold` 画的是同一个圈，收尾完全相反**：`hold` 的圈满是结算（松不松手
不改变结果），`charge` 的圈满只是拉满——弓拉满了不会自己射出去，**松手那一刻才是
那一下**，蓄了几成就是那一刻的 `holdRatio`。分成两个 mode 而不是加一个布尔，是因为
它决定了「松手」有没有含义。

**冷却写在能力上，按物品种类分组**（`Cooldown.Item.<itemType>`）。能力每次用完就被
收回、下次用时重新授予，所以冷却不能挂在「这一条能力实例」上；换手也不该洗掉这把
弹弓的冷却。冷却中的那一下在 `beginItemUse` 就被挡住，而不是等到激活时被 GAS 拒绝
——不挡的话，玩家会先看到一圈画满的蓄力，松手才发现这一下从来没算数。

**吃东西**（`action: "eat"`）就是这套形状的一个用法：按住的那一整段是嘴里在嚼，
圈满 = 咽下去 = 服务端从那一格扣掉 `value` 个。回血还没有：角色身上还没有一条
可回复的属性，有了之后加的是 `eatItem` 里的一行。

嚼的那一段有两件东西在动，**它们读同一份曲线**（`src/player/chewAnimation.ts`）：

| 谁 | 怎么动 | 写在哪 |
| --- | --- | --- |
| 角色模型 | 每一口一顿，上下为主、左右带一点 | `PlayerEntity` 写渲染坐标的那一帧偏移 |
| 手上那件食物 | 一口一口地小下去，咬合那一下还被捏一次 | 实例通道的 `PROP_SCALE` + 同一个位置偏移 |

曲线的输入是**比例**而不是秒数：圈走到哪，嚼就到哪，长按多久都自动对齐。两边各写
一套的话，拍子迟早对不上——玩家在抖、食物在另一个节奏上缩，看起来像两件事同时
发生，而不是一件事。食物的位置偏移和角色是同一个，否则角色抖起来、食物钉在权威
坐标上，两者会当场分开。

整段都是**纯表现**：不过网、不上报、不碰玩法坐标。抖得对不对不改变背包里少了几个。
代价是**只有自己看得见自己在嚼**——别人那边没有这段表现，因为它不在复制里。等
角色动作有了自己的复制通道，这一段挂上去就是；在那之前，为了一段抖动单开一条
网络状态不值得。

**「接下来这一下用的是哪件东西」不能等快照。** 快照 10Hz，菜单里点完「使用」到
下一帧回来有 100 毫秒；玩家在这一段里按下的那一下，如果要等「物品栏账上有没有」
才认，会被整条忽略——表现就是「点了使用，按下去没反应」。所以界面在点的同一刻
就把这件东西交给输入层（`HotbarController.armItem`），服务端那边则由命令顺序保证
（`select` 先到、`use:begin` 后到）。

同样的理由，**一次使用按住认的是「用的哪件东西」，不是嘴上那个 Actor**：换手时
手持表现体会换一个新 id，按 id 判断会把刚开始的这次按住当成「换手了」立刻取消。

### 4.6 交给武器系统的接口

「一件东西用起来到底发生什么」是一张注册表（`server/actors/ItemUseActions.mjs`），
不是一条 switch。内置三条（`eat` / `tool` / `throw`）在那里注册，`shoot` 故意空着：

```js
registerItemUseAction('shoot', (context) => {
  // 弹丸怎么飞、打中了怎么样，全归武器系统。
  // 返回 false 表示这一下什么都没做成（比如没有弹药）。
  return context.consumeAmmo(1) === 1 && spawnProjectile(context);
});
```

这么写是为了让**别的系统自己接进来**：武器系统注册一条执行器就够了，不必回过头改
物品系统，物品系统也不必认识弹丸、伤害、命中判定。没人注册的动词返回 false——那件
东西按下去什么都不发生，而不是抛异常把整个房间 tick 带下去。

执行器收到的 `ItemUseContext` 就是那份接口：

| 字段 | 是什么 |
| --- | --- |
| `scene` / `player` | 房间场景（权威侧）与用这件东西的玩家 |
| `use` | 解析出来的用法：动词、`holdSeconds`、`cooldownSeconds`、`value`、弹药位规格 |
| `source` / `slot` | 这次用的是手上那一格还是包里那一摞；`slot` 是那一格的地址 |
| `heldSeconds` / `chargeRatio` | 按了多久、蓄了几成（`charge` 之外恒为 1），按**服务端**记的时刻算 |
| `consumeItem(n)` | 从这一格扣掉几个（弹弓不消耗自己，果子消耗） |
| `ammo` / `consumeAmmo(n)` | 这一格现在装着的弹药，以及打掉几发 |

扣货和扣弹药做成闭包交出去，而不是把 `InventoryComponent` 摊给执行器：「这次用的是
哪一格」是物品系统算出来的，执行器再推导一遍就有推错到另一本账上的机会。

## 5. 容器：一个箱子，几个人一起翻

`ContainerComponent` 挂在世界 Actor 上，内容记在自己的 `ItemLedger` 里。

**共享靠权威顺序，不靠锁。** 所有存取都在房间 DS 的同一条 tick 线上依次执行，
`ItemLedger.remove` 按账上实际有的数量截断。两个人同时取最后一摞：先到的拿走，
后到的拿到 0，然后各自在下一帧快照里看到真实结果。没有锁、没有独占、没有「正在被
使用」的拒绝态——那些是为了避免竞态而引入的，而这里的竞态本来就有正确答案。

`viewerPlayerIds` 只决定**内容发给谁**，不构成任何独占：

- 没开着箱子的人收不到里面有什么——一屋子箱子不会每帧把全部库存推给所有人；
- 开着的人每帧都收到，所以别人存进去的东西**立刻出现在我的界面上**；
- 走远由服务端移出，不依赖客户端自觉。

玩家自己的背包是私有的：它随 `SnapshotPlayer` 下发，而且**只发给本人**。

## 6. 界面

### 6.1 格子只有一套

背包那一片和下方那条物品栏是**同一种格子**（`createInventorySlotCell`）：同一份
DOM、同一套点击与拖拽、同一个菜单入口。两边各写一遍的话，「点一下弹菜单」这种事
迟早只在其中一边成立，而玩家看到的是两个长得一样却行为不同的方格。差别只剩尺寸
和角标——物品栏要塞进页脚，所以画成小方格、左上角带数字键序号、拿在手上的那一格
描粗，这些由 `variant` 决定，不是另一套实现。

每一格有两条入口，指向同一件事：

- **点一下** = 弹出这一格的动作菜单（快的那条不用打开菜单的人走拖拽）
- **按住拖动** = 直接搬：背包 → 物品栏是装配，物品栏之间是排序，物品栏 → 背包是收回

菜单上永远是三条，做不了的那条列出来但点不动——直接抹掉会让菜单在不同格子上长得
不一样，玩家得先数一遍才知道点的是哪一条。两本账的第三条方向相反：

| | 第一条 | 第二条 | 第三条 |
| --- | --- | --- | --- |
| 背包那一格 | 使用（授予能力，见 §4.5） | 装配（搬进物品栏） | 丢弃（`drop:stack`） |
| 物品栏那一格 | 使用（切到这一格，用法跟着选中格走） | 收回背包（`hotbar:stow`） | 丢弃（`drop:hotbar`） |

物品栏那一格的「使用」发的是 `select` 而不是 `use:arm`：手持物的用法由服务端在切
格的同一刻授予，再发一条 arm 只会让两条能力抢同一个槽位。已经握在手上的那一格
一条都不发——`select` 把「切到当前格」当成收手，再发一次等于把它放下。

「丢弃」在两本账上是两条命令，因为它们说的不是同一堆货：背包那条按 `itemType` 扣
背包，物品栏那条按 `slotIndex` 扣那一格。用一条按 itemType 的命令兼两边，会在两边
都有同一种物品时扣错一本。

容器界面不走格子：一行两个按钮**存 / 取**，外加一个「全部存入」（见 §6.3）。

### 6.2 自动分类，第一页是全部

页签顺序固定：`全部` → 物品目录里 `ITEM_CATEGORIES` 的顺序，空分类不出现。
每页内按（分类序，目录序）稳定排序。

**排序是界面的事，不是账本的事**：账本按「谁先进来谁在前」存放并原样复制，
`buildInventoryView` 每次重排一遍。所以「整理」不是一个按钮，是没有东西需要整理
——顺序既然是推导出来的，就不会乱。

### 6.3 容器界面

一行 = 一种物品，**箱内和身上并排**，右侧两个按钮各搬一个方向，外加一个「全部
存入」。这是不做双面板拖拽的理由：玩家要决定搬哪一边，就得同时看见两边；分成
两个面板再让人拖来拖去，是把这个判断拆散之后再要求玩家自己拼回去。

搬的是整行数量。数量选择器是拖拽之外第二费工的交互，而「全存 / 全取」覆盖了绝大
多数实际操作。

**开合不是本地状态**。界面开着与否跟随服务端的 `container.open`：走远、箱子被
拆、掉线都由服务端把人移出，客户端不各自判一遍距离，也就不会出现「服务端已经关
了但界面还开着，点存取全被拒」。按下交互键只是发一条 `container:open`，界面在下
一帧快照回来时才真的打开。

**关闭是唯一的例外，而且需要一个在途标记。** 快照 10Hz，纯等确认要 100ms 以上
才消失，点 X 会明显发黏，所以界面立刻收起。但 `container:close` 还在路上时，
服务端仍然认为我开着它——`sync()` 会把页面推回来，下一帧才真的关上，表现就是
关闭时闪一下。`pendingCloseActorId` 记的就是这次在途请求：它不是第二个「开着
没有」的真相来源，只是让 `sync()` 在确认到达之前别把它推回来。actorId 变了就
说明确认到账，标记随即清掉，所以走到另一个箱子前按 E 不会被压住。

Esc 也必须走同一条 `requestClose`：CommonUI 的默认弹栈只把页面弹掉、不通知服务
端，于是下一帧快照又把它推回来——那不是闪一下，是**关不掉**。容器页因此关掉
`closeOnEscape`，自己接管 Esc。

「全部存入」逐种发一条而不是发一条「全部」：每种物品的可存量要各自截断（箱子可能
中途装满），拆开之后，装得下的照样进去，装不下的原样留在背包里。

### 6.4 箱盖动画

模型是箱体 + 一块**绕后沿翻起**的盖子（比例取自
`.cursor/demo/line-art-style-magic-cabin-main` 的楼梯下储物箱）。枢轴必须在后沿：
绕自身中心转的话，掀开时盖子会陷进箱体。

过边界的只有一个 0 / 1 的目标 `PARAM_CONTAINER_OPEN_TARGET`——「有没有人开着」是
玩法状态，从关到开的那段回弹是表现。把角度本身过网的话，掉帧和快照抖动会直接抖
到盖子上。渲染侧 `ThreeContainerLidVisual` 用弹簧阻尼积分，因为盖子有重量：线性
插值到位那一下会硬停，看起来像贴图切换而不是一块木板被掀起来。

目标取的是**有几个人开着**而不是「我开着没有」：别人翻这个箱子时，我也该看见盖子
是掀起来的。

### 6.5 重画时机

`revision` 变了才重画。背包内容、快捷栏配置、选中格共用一个 `revision`。

## 8. 已实现与未实现的使用效果

`use.action` 只登记**已经有系统兑现**的效果：

- `eat` → 从那一格（或背包那一摞）扣掉 `value` 个，客户端同时演一段嚼的抖动
- `tool` → `GeneratedPropComponent.applyDamage(value)`
- `throw` → 掉落物的 `DropMotionComponent` 抛体，初速度 = `value / 10`
- `shoot` → **还没有执行器**：它是留给武器系统注册的那一条（§4.6）。在那之前弹弓
  拉得满、冷却也走，但松手那一下什么都不会飞出去

「吃下**回血**」还不在其中：角色身上还没有一条可回复的属性。所以 `eat` 现在兑现
的是「吃掉一个」这件事本身——那一格真的少一个，是玩家看得见的结果，不是一个按下
去没反应的动词。回血那条属性到位之后，加的是 `eatItem` 里的一行。

`tool` 与 `throw` 的执行器都还在，但**目录里暂时没有物品在用它们**：物品表上没有
投掷物，也没有工具。它们不是死代码里的猜想——两条链路都跑得通、都有过测试——但
在有对应物品之前，谁都按不出来。等这类物品回到物品表时，加的是目录里的一条数据。
