# Common DSL prompts

Read this reference for every SkyLand design-note DSL task involving `@` syntax or the global markers `@design`, `@advice`, and `@todo`. It contains no gameplay landing details.

# 这套记法是什么

上面那几段是 SkyLand 设计稿里的一套**领域特定语言（DSL）**。它不是给程序读的格式，
是给**人和 AI 一起读**的格式：策划在 Markdown 里用它写下一件东西**是什么**，
实现方照着它把这件东西落成仓库里的配置与代码。

它解决的是设计稿的老问题：同一件物品，在一段散文里写着「果子能吃，最多叠 10 个」，
落地时要拆成图标、模型、堆叠上限、使用方式四处配置，散文里少写一条就少配一处，
而且看不出少了哪条。`@i` 这样的条目把「一件东西需要交代清楚的字段」固定下来——
**字段缺了是看得见的**，缺的那条就是要么补设计、要么标 `@design`。

用它的文档目前是：

| 文档 | 用到的定义 |
| --- | --- |
| [`doc/designer-inventory.md`](../../../../doc/designer-inventory.md) | `@i` 物品表 |
| [`doc/designer-toolandweapon.md`](../../../../doc/designer-toolandweapon.md) | `@i` / `@b` / `@w`——重炮就是三条合起来的一件重型工具 |
| [`doc/desinger-buildsys.md`](../../../../doc/desinger-buildsys.md) | 建造件的散文设计，`@b` 的取值来源 |

**这份文档只定义记法本身。** 某一类东西**当前有哪些**，看上面那几份设计稿；
某一件东西**最终长什么样**，看 `config/` 里的 JSON。三者不重复：记法在这里，
内容在设计稿，事实在配置。

# 通用语法

```text
* @<类型字母> <名称>: <一句话说明>
    * <字段键>: <值>
    * <字段键>: <值>
        * <子字段键>: <值>
```

规则：

* `@` 是这套 DSL 唯一的指令前缀：后面可以是**类型字母**（`@i` / `@b` / `@w`，起一条定义），
  也可以是标记或请求（`@todo` / `@design` / `@advice`）。看到 `@` 后按紧跟的单词机械判断含义。
* 统一用 `@` 而不用 `#`，因为 `#` 在 Markdown 中表示标题，尤其出现在行首时会被解析成文档结构；
  `@` 没有这层冲突，也让规则保持干净：**`#` 只管 Markdown 标题，`@` 只管 DSL 指令。**
* **条目头**是 `@` 紧跟一个类型字母，然后是名称。名称用中文，就是玩家看到的显示名。
  冒号后面是一句话说明；一件东西如果名字已经说清楚了（比如 `@i 木头`），说明可以省掉。
* **字段行**是条目下一级的列表项，`键: 值`。键是上面各节规定的单字母或短词，
  **大小写敏感**。
* `<>` 里写的是**这个位置该填什么**，不是要照抄的字面量。上面各节的 `<>` 是字段释义，
  下面写实际条目时把它换成具体内容。
* 字段**没有顺序要求**，但按各节列出的顺序写，读的人扫得快。
* **写 `0` 或整行不写 = 没有这一项。** 这条对 `R`（耐久）、`B`（关联建筑）都成立。
* 引用另一条定义时**写它的名称**，不写 id。`@w 石斧` 的 `I: 石斧物品` 指的是
  某个 `@i 石斧物品`。被引用的条目要在同一份或另一份设计稿里真的存在。
* `@design` 放在值的位置，意思是**这一条故意留白，由实现方提出一个合适的设计**：
  「这条我知道它需要存在，但我不指定」，要给出答案并把答案写回条目里。
  整行缺失和 `@design` 不一样——前者是漏了。它**后面可以跟参数**指定设计完做什么
  （`(do)` / `(w)` / `(s,n)`），不带参数只出方案不写代码。
* `@advice` 是它的对偶：`@design` 填空白，`@advice` 改**已经写好的内容**，参数同一套。
  两者和 `@todo` 的分工见下面「标记」一节。
* 中英文冒号在设计稿里都出现过（`F：` 和 `F:`），读的时候两个都认。**新写的用半角 `:`。**

## 类型字母

| 字母 | 类型 | 定义节 | 落地去处 |
| --- | --- | --- | --- |
| `@i` | 物品：进得了背包、算得清数量的东西 | [物品定义](#物品定义) | `config/items/item-catalog.json` + 一个掉落物 Actor 原型 |
| `@b` | 建筑件：按网格放到世界里的东西 | [建筑定义](#建筑定义) | `config/actors/<id>.actor.json` 的 `buildPiece` Component |
| `@w` | 工具 / 武器：拿来对别的东西产生效果的东西 | [武器、工具定义](#武器工具定义) | 尚无专属配置，见下文「落地映射」 |
| `@e` | 实体：怪物、NPC 这类自己会动的东西 | 正在设计中 | — |

一件东西可能同时需要两条定义：篝火既是背包里的一摞 `@i 篝火物品`，
又是放出去之后的那个 `@b 篝火`。这时候写两条，用 `I:` 互相指过去，不要合成一条。

## 标记：`@todo`、`@design`、`@advice`

三个都表示「这里还差点什么」，但差的**不是同一样东西**，读到时要做的事也不同：

| 标记 | 差的是 | 你该做什么 |
| --- | --- | --- |
| `@design` | **设计**。这一处空着，或只写了个方向 | 把它补成一个完整方案写回去；做到哪一步由它的参数说了算 |
| `@advice` | **更好的做法**。这一处已经写完整了 | 审视现有内容并提优化建议；做到哪一步同样由参数说了算 |
| `@todo` | **实现**。设计已经定了，代码还没写 | 照着已有的设计去实现，不要重新设计 |

**位置不决定用哪个标记，起点才决定。** 三个都能标在整块或某一行的行尾，`@design`
还能直接填在值的位置。所以下面几种都是对的：

* `T: @design` —— 这个值是空的，从无到有给一个
* `* bpf-slime的死亡动画、状态 @design` —— 这一行点到的东西还缺设计
* `* Effect: 受到攻击力的伤害，按照蓄力倍率缩放 @design` —— 这一行只写了一半，剩下的你补

选哪个标记看的是**这一处缺什么**：一点都没有或只写了个方向 → `@design`；已经写完整、
只是想让它更好 → `@advice`；写完整且不用改、只差代码 → `@todo`。

一处标了 `@design` 或 `@advice` 就隐含还没实现，不用再补一个 `@todo`；反过来不成立——
一条设计写得清清楚楚的 `@todo` 只是还没轮到它。

作用范围：

* 标在**模块标题**上（上一行或标题上方那个空行）：这一节连同下面所有条目都没实现。
  这时**下面不必每条再标一遍**，整块已经盖住了。
* 标在**某一行行尾**：只有这一行没实现。它周围的兄弟条目不受影响。
* 一条 `@i` / `@b` / `@w` 标了 `@todo`，**它仍然是一条完整有效的定义**——字段该写全还得写全，
  标记只说它还没落地，不说它可以写得潦草。

`@todo` 记的是**某一条内容**有没有实现；本文档各落地映射表的「现状」栏记的是
**某一个字段**有没有系统承接。两者层级不同，不要互相抄。

### `@design` 和 `@advice` 的参数

这两个标记不只说「这里还差点什么」，还说明**做完之后该做什么**。参数写在括号里，
**两者用同一套**：

| 写法 | 叫什么 | 出了方案之后做什么 |
| --- | --- | --- |
| `(do)` | design-only | 把结果填回 md 的这个位置，去掉标记，这条改标 `@todo`。**不写代码** |
| `(w)` | write | 把结果填回 md，**并且直接实现**。实现完不留 `@todo` |
| `(s,n)` | select | 给出 **n 个不同方向**，说清各自的取舍，**问用户选哪一个**。不要自己替用户定 |
| 不带参数 | | 按 `do` 办 |

两者的差别只在**起点**，不在参数、也不在位置：`@design` 面对的是一处**空白或半成品**，
要把它补成一个完整方案；`@advice` 面对的是**已经写完整的内容**，要指出它哪里可以更好。
两者都能标在行尾，`@design` 还能直接填在值的位置。

**不带参数按 `do`**：只出方案，不写代码。这条是故意保守的——把一处只想要方案的地方
当成动手实现的许可，代价比反过来大得多。真要顺手实现就明写 `(w)`。

`(s,n)` 的 n 个方向必须是**真的不同的方向**，不是同一个方案换三种措辞；每个都要说清
它换来什么、付出什么。用户选定之后，按 `do` 收尾：把选中的那个填回去，改标 `@todo`。
想选完就直接实现的，用户在选的时候说一声就是。

`@advice` 有一个 `@design` 没有的正当结局：**看完觉得不用改**。这时去掉标记并说明
为什么现在这样就挺好，不要为了交差硬凑一条建议。`@design` 没有这个出口——那个位置
是空的，总得填上点什么。

几个标记连起来就是一条内容的完整生命周期：

```text
@design(...)          缺设计
@advice(...)          有内容，可能能更好
      │ 出了方案，填回 md
      ▼
@todo                 有方案，缺实现        ← (do) 停在这里
      │ 实现完，去掉标记
      ▼
（无标记）             已落地               ← (w) 一步走到这里
                                          ← @advice 判定「不用改」也到这里
```

所以 `@design` / `@advice` 处理完**一定会留下痕迹**：要么变成 `@todo`，要么变成没有
标记的成品。留着原样的标记意味着这一处还没被处理过。
